## Распределение модулей

Поскольку нас четверо, а не восемь, каждый берёт на себя примерно по два связанных модуля. Распределение учитывает зависимости — модули, от которых зависят другие, идут в первую очередь.

### Сержан (тимлид) — Системное ядро + интеграция

**Зоны ответственности:**

- `UniversitySystem` (Singleton) — главный контейнер состояния системы
- `DataStorage` — сериализация состояния через `ObjectOutputStream`
- `Main.java` — консольный интерфейс и demo-сценарий
- Координация PR, ревью кода, сборка финального проекта
- `AuthenticationException` и общая логика логина
- Интеграционное тестирование

**Почему это блокирующий модуль:** все остальные обращаются к `UniversitySystem.getInstance()` для доступа к спискам пользователей, курсов, новостей. Этот модуль должен быть готов первым, иначе никто не сможет интегрироваться.

### Ергали — Пользователи и аутентификация

**Зоны ответственности:**

- Иерархия `User` → `Employee` → `Teacher`/`Manager`/`Admin`/`ResearchEmployee`
- `Student` (наследник `User`)
- `UserFactory` (паттерн **Factory**) — генерация ID с префиксами:
  - `EMP-*` для сотрудников
  - `BD-*` для бакалавров, `MP-*` для магистров, `PHD-*` для докторантов
- `equals`/`hashCode`/`toString` для всех классов
- Реализация `getRole()` для каждого подкласса
- Логика `login(String pwd)` совместно с Сержаном
- Перечисления `TeacherTitle`, `ManagerType`, `StudentYear`, `Role`

**Ключевые требования из ТЗ:**
- Преподаватели в звании `PROFESSOR` обязательно являются Researcher
- Бакалавры могут быть Researcher (опционально)
- `Employee` может быть Researcher без преподавания

### Фархат — Академический модуль

**Зоны ответственности:**

- `Course` — управление курсом, список инструкторов, список зачисленных, проверка предусловий
- `Lesson` — типы занятий (`LECTURE`/`PRACTICE`), расписание, метод `conflictsWith` для проверки конфликтов
- `Mark` — структура `ATT1` + `ATT2` + `Final`, расчёт итоговой оценки, буквенная шкала, GPA-баллы
- `Transcript` — академическая справка студента, расчёт GPA, список проваленных курсов
- `Student.registerForCourse(Course)` — самая важная функция системы (по ТЗ)
- Все исключения регистрации:
  - `CreditLimitExceededException` (лимит 21 кредит)
  - `MaxFailuresException` (максимум 3 провала)
  - `PrerequisiteNotMetException`
  - `CourseRegistrationException`
- Перечисления `LessonType`, `Semester`, `AttestationType`, `Major`

**Критичные правила из ТЗ:**
- Студент не может иметь более 21 кредита одновременно
- Студент не может проваливать курсы более 3 раз
- Курс может иметь несколько инструкторов
- Должны быть проверены предусловия перед регистрацией

### Дияр — Исследовательский модуль и менеджмент

**Зоны ответственности:**

- `Researcher` (интерфейс) — `getPapers()`, `getProjects()`, `getHIndex()`, `printPapers(Comparator)`
- `ResearchProfile` — расчёт h-индекса, хранение публикаций и проектов
- `ResearchPaper` — поля по стандарту IEEE (минимум 5–10: title, authors, journal, doi, datePublished, citations, pages, abstract, keywords)
- `ResearchPaperBuilder` (паттерн **Builder**)
- `ResearchProject` — добавление участников с проверкой `instanceof Researcher`
- Три компаратора (паттерн **Strategy**): `ByDateComparator`, `ByCitationsComparator`, `ByPagesComparator`
- `Manager` — методы одобрения регистрации, назначения курсов, генерации отчётов
- `News` + `NewsService` + `NewsObserver` (паттерн **Observer**)
- `ReportGenerator` — отчёты по успеваемости
- Поддержка назначения научного руководителя для 4-го курса (с проверкой h-index ≥ 3)
- Исключения: `LowHIndexException`, `NotAResearcherException`
- Перечисления `UrgencyLevel`, `NewsCategory`, `RequestStatus`

**Критичные правила из ТЗ:**
- Если научному руководителю назначается человек с h-index < 3 → выбрасывается `LowHIndexException`
- Если в `ResearchProject` пытается вступить не-Researcher → выбрасывается `NotAResearcherException`
- Топ-цитируемые исследователи школы и года

## Календарный план — три спринта

### Спринт 1 — Каркас и базовая функциональность (3–4 дня)

**Цель спринта:** к концу недели всё компилируется и можно запустить `Main.java`, который выполняет минимальный сценарий: создание пользователя → логин → выход.

**Сержан:**
- Реализовать `UniversitySystem`: `getInstance()`, поля `users`, `courses`, `news`, `logs`, методы добавления/удаления
- Реализовать `DataStorage.serialize()` и `deserialize()` через `ObjectOutputStream`
- Сделать заглушку `Main.java` с меню логина

**Ергали:**
- Реализовать конструкторы `User`, `Employee`, `Student`, `Teacher`, `Manager`, `Admin`, `ResearchEmployee`
- `equals`/`hashCode` (по `id`), `toString`
- `UserFactory.createStudent(...)`, `createTeacher(...)`, и т.д. с префиксной генерацией ID
- Метод `login(String pwd)` сравнивает пароль через `BCrypt` или хотя бы хеширование SHA-256
- Все `getRole()` возвращают правильную константу `Role`

**Фархат:**
- Реализовать конструкторы `Course`, `Lesson`, `Mark`, `Transcript` с геттерами/сеттерами
- Заглушки методов (пока без бизнес-логики)
- `Mark.calculateTotal()` по формуле `ATT1 * 0.3 + ATT2 * 0.3 + Final * 0.4`
- `Mark.getLetterGrade()` — стандартная шкала КБТУ (A=95+, A-=90+, B+=85+, и т.д.)

**Дияр:**
- Реализовать конструкторы `ResearchProfile`, `ResearchPaper`, `ResearchProject`, `News`, `NewsService`
- `ResearchPaperBuilder` с fluent-API (методы возвращают `this`)
- Три компаратора `ByDateComparator`, `ByCitationsComparator`, `ByPagesComparator` — пока с базовой логикой `Integer.compare()`/`LocalDate.compareTo()`

**Контрольная точка спринта 1:** общая встреча, демонстрация в Telegram-чате, что у всех всё компилируется и базовые объекты создаются. Если кто-то отстаёт — перераспределение нагрузки.

### Спринт 2 — Критичная функциональность (5–6 дней)

**Цель спринта:** работают все три ключевые операции из ТЗ — регистрация на курс, выставление оценок, исследовательская работа. Все кастомные исключения выбрасываются в нужных местах.

**Сержан:**
- Полный логин-флоу с обработкой `AuthenticationException`
- `UniversitySystem.printAllResearchersPapers(Comparator)`
- `UniversitySystem.topCitedResearcher()` и `topCitedOfYear(int year)`
- Логирование действий пользователей (запись в `List<LogEntry>`)
- Сериализация работает round-trip (сохранили → перезагрузили → данные идентичны)
- Расширить `Main.java`: меню по ролям (студент видит свои опции, преподаватель — свои)

**Ергали:**
- `Admin.addUser/removeUser/updateUser/viewLogs`
- `Employee.sendMessage/sendComplaint/sendRequest`
- `Student.rateTeacher(Teacher, int rating)` — хранение рейтингов
- Проверка: профессоры обязательно являются Researcher (валидация в конструкторе или сеттере звания)
- Назначение научного руководителя для 4-курсников с выбросом `LowHIndexException` при h-index < 3

**Фархат:**
- `Student.registerForCourse(Course)` — все 4 проверки:
  1. `course.hasPrerequisitesMet(student)` → `PrerequisiteNotMetException`
  2. `student.currentCredits + course.credits <= 21` → `CreditLimitExceededException`
  3. `student.failedCourses.size() < 3` → `MaxFailuresException`
  4. `!course.isFull()` → `CourseRegistrationException`
- `Teacher.putMark(Student, Course, Mark)` — выставление оценки с проверкой, что преподаватель действительно ведёт этот курс
- `Transcript.calculateGPA()` — расчёт по всем оценкам с учётом кредитов
- `Course.hasPrerequisitesMet(Student)` — проверка завершения предыдущих курсов
- `Lesson.conflictsWith(Lesson other)` — проверка пересечения по времени и аудитории

**Дияр:**
- `ResearchProfile.calculateHIndex()` — корректная формула: максимальное `h` такое, что у автора есть `h` статей с цитированием ≥ `h`
- `ResearchProfile.printPapers(Comparator)` — сортировка и вывод
- `ResearchProject.addParticipant(User)` — `instanceof Researcher`, иначе `NotAResearcherException`
- `Manager.approveRegistration(Student, Course)` — финальное одобрение регистрации
- `Manager.assignCourseToTeacher(Course, Teacher)`
- `Manager.generateAcademicReport()` через `ReportGenerator`
- `NewsService.publish(News)` уведомляет всех подписчиков через `update(News)`
- Регистрация всех `User`-наследников как подписчиков `NewsObserver`

**Контрольная точка спринта 2:** интеграционный тест в `Main.java`. Запускается demo-сценарий end-to-end.

## Правила работы команды

### Git workflow

- Главная ветка: `main`, защищена, прямые push'ы запрещены
- Каждый работает в своей ветке: `feat/users-auth`, `feat/academics-registration`, `feat/research`, `feat/system-core`
- Коммиты по Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`)
- Перед merge — обязательное ревью одного другого участника
- Перед merge `mvn compile -q` должен проходить без ошибок

### Дисциплина

- **Ежедневный апдейт в Telegram-чате** (2–3 строки): что сделал сегодня, что блокирует, что планирую завтра. Это станет материалом для раздела «Проблемы и управление проектом» в финальном отчёте.
- **Сигнатуры публичных методов заморожены** после спринта 1. Если нужно изменить сигнатуру — пишем в чат, обсуждаем, обновляем диаграмму, потом меняем код.
- **Не пушить сломанный код в `main`.** Если ваша ветка ломает `Main.java`, чините до merge.
- **Тесты вручную в Main.java** при каждой реализации. Полноценный JUnit опционален, но `Main.java` должен запускаться end-to-end после каждого merge.

### Telegram-чат для отчёта

ТЗ требует ссылку на чат команды и скриншоты обсуждений. Поэтому:

- Все рабочие обсуждения ведём в одном Telegram-чате (не в личках!)
- Скриншоты ключевых моментов сохраняем сразу — потом будет лень искать
- Особенно ценно: обсуждения архитектурных решений, баги и их решения, разногласия и компромиссы

## Краткая дорожная карта

```
Сегодня → Спринт 1 (3–4 дня): каркас компилируется, базовые операции работают
Спринт 1 → Спринт 2 (5–6 дней): критичная функциональность + все исключения
Спринт 2 → Спринт 3 (3–4 дня): demo, документация, отчёт, презентация
Финальный экзамен: сдача, устный ответ
```

**Главный риск:** интеграционный долг. Восемь рук в команде из четырёх человек требуют, чтобы каждый видел общую картину. Чините `Main.java` сразу, если ваш модуль его ломает. Не оставляйте интеграцию на последний день.

**Главный фокус по ТЗ:** «MOST IMPORTANT FUNCTIONALITY — course registration, putting marks, research. Finish it first.» Это значит, что в спринте 2 мы прицельно добиваем именно эти три потока. Всё остальное — бонусы.
